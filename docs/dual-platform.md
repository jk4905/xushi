# 双端维护约定

## 交付单位

一项产品需求包含 H5 与微信小程序的对应实现、回归和验证记录。默认同时维护；仅当用户明确指定单端时才收窄。不是要求两套代码写法相同，而是让两端完成相同任务并保留相同业务结果。

## 代码入口

| 内容 | H5 | 微信小程序 | 维护方式 |
|---|---|---|---|
| 页面 / 路由 | `weekend-menu-prototype.html` 的 `app-logic` | `pages/*`、`app.json` | 两端分别修改 |
| 样式 / 动效 | HTML 内样式、`weekend-menu-c.css` | `app.wxss`、页面 / 组件 WXSS | 两端分别修改，按平台实现 |
| 主导航 | HTML 页面壳与 Tab 处理 | `components/app-tabs`、`custom-tab-bar` | 检查全部调用方 |
| 餐次模型 | HTML 的 `script#meal-logic` | `core/meal.js` | H5 为源，生成小程序副本 |
| 家庭 / 菜谱 / 菜单模型 | `weekend-household-model.js` | `core/household.js` | H5 为源，生成并保留平台适配 |
| 原始三道菜谱 | HTML 的 `beefSteps` 等数据 | `core/content.js` | 从 H5 原文生成，不推测缺失内容 |
| 存储 / 恢复 | HTML 中的 localStorage、草稿与位置处理 | `core/store.js`、`core/adjustment.js` | 平台独立；共同验证数据结果 |
| 原始动作图 | HTML 的 SVG 图示 | `assets/*.png` | 已提供 PNG；图示变化时用现有 `sync-h5.cjs --images` 重新生成 |

表中 H5 文件均在 `h5/`，小程序文件均在 `miniprogram/`。本轮保留已有模型抽取方式，不引入新框架或运行时共享包。

## 改需求时的顺序

1. 写出用户操作、成功结果、取消 / 失败结果，定位两端页面和受影响模型。
2. 模型变化先改 H5 权威来源，运行 `npm run sync`；生成文件和源文件一起提交。
3. 分别调整 H5 与小程序的页面、路由、存储适配或动效。不要把生成模型视为已完成小程序页面改动。
4. 运行 `npm test`；它包含 H5 四套现有回归、小程序测试、只读模型一致性和工程结构检查。
5. 按下表验收受影响的行为，分别记录两端结果。未运行、不支持或受限的项目标明原因。
6. 在同一提交 / PR 中交付两端；使用 PR 清单核对遗漏。

## 共同业务契约

| 操作 | 两端都应保留的结果 |
|---|---|
| 清单勾选 / 取消 | 原行直接修改；不重排、不抢滚动；不能自动完成一餐 |
| 开始做饭 | 一次主操作进入做法，不增加配方核对关卡 |
| 阅读 / 换菜 / 切 Tab | 完整做法可连续阅读；餐次与菜谱隔离；回来继续原进度 |
| 本餐调整 | 保存返回来源；原菜谱不被本餐修改覆盖 |
| 保存失败 | 留页保留输入，不假报成功；恢复后重试不重复创建 |
| 完成这一餐 | 显式确认；看完做法不会自动完成，取消不改状态 |
| 备份 | 保留 schema v2 与 v1 迁移兼容，跨端导入导出；不能静默丢字段 |
| 原始配方 | 牛肉原文、西芹保留；西兰花 / 米饭缺失的做法和用量不编造 |

## 允许的平台差异

- H5 使用浏览器来源隔离的 localStorage；小程序使用微信设备本地存储。代码同步不代表用户数据自动同步。
- 微信单条存储有容量约束；当前小程序有效家庭数据上限 900 KB、导入文件上限 4 MB，H5 可能有更大的可用容量。必须明确报错，不能截断数据。
- H5 和小程序的导航、键盘、安全区、动画 API 不同；采用平台实现，分别验证。已存在的视觉/动效差异不因本次代码搬迁自动消除。
- 外部链接在小程序中复制后查看，不能声称已具备第三方解析能力。

## 自动检查能证明什么

`npm run check:sync` 会重新计算三个生成文件并与磁盘内容比较，漂移时失败，且不自动修改源文件或生成文件。它能发现模型副本漏更新或被手改，不能发现界面需求只做了一端。

GitHub Actions 在 push / PR 执行全部回归和一致性检查。两端界面是否都落实需求，仍需代码评审、PR 清单与两端运行证据。不要以测试数量替代体验验收。
