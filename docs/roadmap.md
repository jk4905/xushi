# 迭代规划与已确认取舍

更新：2026-11-08。这里区分已确认范围、待验证方向和历史方案，没有承诺开发日期，也不授权自动新增功能。

## 当前重点：把一顿饭做顺

已确定主线：两个 Tab → 选菜 / 常做菜单 → 买菜 → 完整图文做法 → 明确完成。链接录入先保存来源，已有材料与步骤可以手动补充。后续需求同时维护 H5 和小程序。

近期优先补使用证据：

1. 在 iPhone 上用真实一餐复验大字号、键盘、底栏、安全区与点按反馈。
2. 验证中断、换菜、切 Tab、同会话刷新以及失败重试；对照 [双端差异](interaction.md)，不把静态稿的理想状态当作已实现。
3. 观察链接 + 菜名是否足够轻便，用户何时愿意补材料与做法。先记录阻碍，不预设必须上 AI。
4. 检查当前动效与减少动态效果是否一致；改善手感时保持已接受 UI 和业务行为。

进入下一阶段的依据应是重复使用中出现的具体问题，而不是新增页面数量或设计评分。

## 后续方向（未排期）

| 方向 | 用户价值假设 | 推进前需要验证 |
|---|---|---|
| 更省事的菜谱录入 | 减少从原链接手工整理材料 / 做法的工作 | 常用来源、实际录入成本、提取准确性、来源标注和失败后的人工修正方式 |
| 工作日快手菜 / 周末备餐 | 更容易决定做什么、买什么 | 一人实际复用情况、时间与食材约束、需要一餐还是多餐计划 |
| 健身吃什么 / 一周备菜 | 将目标、采购与备餐结合 | 是否有稳定需求，数据依据和建议边界，不能把模型输出直接称为准确营养评估 |
| 日常外食 / 外卖选择 | 降低上班周边“吃什么”的决策成本 | 与家庭下厨是否是同一个主要任务，数据来源和维护成本 |
| 旅游当地吃什么 | 保存和选择地方特色 | 地点信息、内容来源与实用性；不默认并入当前 Tab |
| 宝宝 / 孕妇 / 老人 / 病人饮食 | 按特定限制找食物 | 有可靠专业依据与清楚边界之后再评估，不先用泛化 AI 生成忌口结论 |
| 做饭与保存好物 | 帮助采购、保存和快速制作 | 真实使用反馈及其与当前流程的关联，不为广告增加入口 |
| 其他人发布 / 社区 | 汇集可复用的真实菜谱与经验 | 先验证个人工具价值，再评估内容质量、维护量和单人运营能力 |

朋友忌口记录、用餐人和厨具档案曾讨论，但已明确退出 MVP；只有新的真实需求成立且用户重新确认后才考虑恢复。

## 盈利验证（假设，未实现）

可能方向包括经实际制作验证的菜单 / 备餐内容、进阶工具订阅，以及长期内容 / 好物合作。当前没有支付、订阅、广告或社区模块，也没有付费意愿与收益验证。先观察持续使用，再用小范围、具体交付验证是否有人愿意付费；不据兴趣、点赞或自用反馈推导市场规模。

## 不再作为当前开发依据的旧方案

| 旧方案 | 当前决定 |
|---|---|
| 做饭 / 计划 / 收藏 / 我的四个 Tab | 做饭 / 菜谱两个 Tab，餐次和备份为二级入口 |
| 单独本餐详情与下厨总览 | 减少中转；清单直接到完整做法 |
| 上一步 / 下一步逐段确认 | 长文连续图文阅读，一点换菜 |
| 买齐后再次核对配方与用量 | 不设重复关卡；本餐调整为可选分支 |
| 首页展示常做菜单库和多组按钮 | 菜谱里管理，安排一餐时选择 |
| 自动根据偏好剔除西芹 | 保留原配方，用户按本餐需要决定 |
| 用餐人 / 口味 / 厨具设置为 MVP 入口 | 暂不做；旧数据仅保留兼容 |

归档设计图可能仍含旧阶段条、编辑页 Tab 等细节。它们不恢复上述旧方案；采用当前 [PRD](prd.md)、[交互规格](interaction.md) 与 [图稿差异说明](design/README.md)。
